# პრაქტიკული დავალება: გუნდური მუშაობა, კოლაბორაცია და კონფლიქტები Git-სა და GitHub-ზე

## მიზანი

რეალურ სამუშაო გარემოსთან მიახლოებული გამოცდილება: როგორ მუშაობს ორი დეველოპერი ერთსა და იმავე რეპოზიტორიუმზე პირდაპირ `main` branch-ზე, როგორ ანაწილებენ სტრუქტურას და როგორ უმკლავდებიან პირველ რეალურ **Merge Conflict**-ებს.

## პირობები და გუნდის შემადგენლობა

* **გუნდის ზომა:** 2 სტუდენტი (მონაწილე A და მონაწილე B).

* **შესრულების ფორმატი:** საერთო საჯარო (Public) GitHub რეპოზიტორიუმი.

* **მთავარი გამოწვევა:** კოდის ერთობლივი წერა ბრენჩების გამოყენების გარეშე (`main` branch-ზე პირდაპირი `push`-ებით), რათა შეეჯახოთ კონფლიქტებს.

## პროექტის აღწერა: მრავალგვერდიანი ვებ-აპლიკაცია (Mini Portfolio & Blog)

იმისათვის, რომ იფიქროთ კოდის დაორგანიზებაზე, ფაილების სტრუქტურასა და შეთანხმებაზე, უნდა შექმნათ მცირე ზომის, 3-გვერდიანი საინფორმაციო ვებ-გვერდი შემდეგი სტრუქტურით:

1. `index.html` (მთავარი გვერდი - Hero სექცია, ზოგადი ინფორმაცია).

2. `about.html` (ჩვენს შესახებ / გუნდის წევრების ბიოგრაფია).

3. `contact.html` (კონტაქტების გვერდი და ფორმა).

4. საერთო სტილი: `style.css` (ყველა გვერდისთვის საერთო დიზაინი).

## ნაბიჯ-ნაბიჯ შესრულების ინსტრუქცია (Workflow)

### ნაბიჯი 0: წინასწარი შეთანხმება (Architecture & Planning)

სანამ კოდის წერას დაიწყებთ, **აუცილებლად** გაიარეთ კონსულტაცია ერთმანეთთან:

* ვინ რომელ გვერდზე იღებს პასუხისმგებლობას? (მაგალითად: მონაწილე A აკეთებს `index.html`-ს, ხოლო მონაწილე B `about.html`-ს).

* ვინ აწყობს საერთო `style.css`-ის საწყის კოდს და კლასების სახელებს, რომ დიზაინი აეწყოს?

### ნაბიჯი 1: რეპოზიტორიუმის შექმნა და მიწვევა (მონაწილე A)

1. მონაწილე **A** ქმნის **საჯარო (Public)** რეპოზიტორიუმს GitHub-ზე (მაგალითად, სახელით `mini-project`).

2. რეპოზიტორიუმის შექმნისას აუცილებლად მონიშნეთ **"Add a README file"**.

3. გადადით პარამეტრებში: `Settings` -> `Collaborators` -> `Add people` და მიწვიეთ მონაწილე **B**.

4. მონაწილე **B** იღებს მოწვევას და ხდება რეპოზიტორიუმის თანაავტორი.

### ნაბიჯი 2: საწყისი კლონირება (ორივე მონაწილე)

ორივე სტუდენტი აკეთებს რეპოზიტორიუმის კლონირებას საკუთარ კომპიუტერში:

```
git clone <repository-url>
cd mini-project

```

### ნაბიჯი 3: პირველი განაწილებული ცვლილებები

1. **მონაწილე A:** ქმნის თავის წილ ფაილებს (მაგალითად, `index.html`), აკეთებს commit-ს და უშვებს `main` branch-ზე:

   ```
   git add index.html
   git commit -m "feat: add main page structure"
   git push origin main
   
   ```

2. **მონაწილე B:** სანამ თავის კოდს ატვირთავს, აუცილებლად აკეთებს სინქრონიზაციას:

   ```
   git pull origin main
   
   ```

   ამის შემდეგ ქმნის თავის გვერდს (`about.html`), აკეთებს commit-ს და უშვებს `main` branch-ზე:

   ```
   git add about.html
   git commit -m "feat: add about page"
   git push origin main
   
   ```

### ნაბიჯი 4: კონფლიქტებთან შეჯახება (Merge Conflict Challenge)

იმისათვის, რომ გამოსცადოთ რა ხდება კონფლიქტის დროს, შეასრულეთ შემდეგი სავალდებულო ნაბიჯი:

1. ორივემ გახსენით საერთო ფაილი (მაგალითად, საწყისი `README.md` ან ერთ-ერთი HTML ფაილის ზუსტად იგივე ხაზი).

2. **მონაწილე A** ცვლის ამ ხაზს თავის კომპიუტერში, აკეთებს commit-ს და ატვირთავს GitHub-ზე:

   ```
   git add .
   git commit -m "update: change main title by A"
   git push origin main
   
   ```

3. **მონაწილე B**-ს ჯერ არ გაუკეთებია `git pull`. ისიც ცვლის ზუსტად იმავე ფაილის იმავე ხაზს თავის კომპიუტერში, აკეთებს commit-ს და ცდილობს ატვირთვას:

   ```
   git add .
   git commit -m "update: change main title by B"
   git push origin main
   
   ```

4. **რა მოხდება?** GitHub არ მიიღებს მონაწილე B-ს ფუშს და დაუბრუნებს შეცდომას (**Merge Conflict**).

5. **კონფლიქტის მოგვარება:** მონაწილე B-მ უნდა გააკეთოს `git pull`, გახსნას კონფლიქტური ფაილი, ხელით გაასწოროს Git-ის მიერ დატოვებული ნიშნულები (`<<<<<<<`, `=======`, `>>>>>>>`), აირჩიოს სასურველი ვერსია, გააკეთოს ახალი commit და წარმატებით ატვირთოს (`git push origin main`).

## ჩაბარება

გამოაგზავნეთ საჯარო GitHub რეპოზიტორიუმის ლინკი. Commit-ების ისტორიაში მკაფიოდ უნდა ჩანდეს როგორც ერთობლივი მუშაობა, ისე კონფლიქტის წარმატებით მოგვარების ისტორია.
